**How publishing works.** Source verification is a compile-and-compare: the explorer receives the
exact compiler input and re-compiles it, and publishes the sources only if the output matches the
bytecode on chain — so a verified page is cryptographic evidence that the displayed sources are the
deployed code, not an attestation by the submitter. What gets submitted, per contract:

1. the **standard JSON input** — the full compiler input (all source files + settings) emitted by
   `forge verify-contract --show-standard-json-input` from the repo at the pinned deploy commit;
2. the **compiler version** (`v0.8.34+commit.80d5c536`, from the build artifact metadata); and
3. the **ABI-encoded constructor arguments** — recovered from the actual creation transaction in the
   deploy broadcast (creation input minus compiled initcode), never re-derived from configs, so they
   match the deployed bytecode by construction.

Delivery differed per explorer, same payload everywhere: Arbitrum + Linea through the Etherscan v2
API (`just verify-sources`, free-tier chains); Optimism + Base through the web "Verify & Publish"
form (their API verification submissions are paid-plan-gated — see below); Sourcify through its v2
API (`POST sourcify.dev/server/v2/verify/<chainId>/<addr>`), which grades the strictest result —
**exact_match** for creation *and* runtime bytecode. The Blockscout instances then auto-imported the
Sourcify matches without a separate submission, and Etherscan's cross-chain bytecode matching
auto-verified several instances once identical code was verified on the free-tier chains.

> **Why a paid plan?** Since the family explorers merged into the unified Etherscan API V2, chain
> access is a plan feature: the official
> [supported-chains table](https://docs.etherscan.io/supported-chains) lists Optimism (10) and
> Base (8453) as paid-plan chains, while Arbitrum (42161) and Linea (59144) are on the free tier.
> There is no technical difference — the same key verified Arbitrum/Linea. Source-code *read*
> endpoints are exempt ("available on all chains for every API plan"), which is why the source
> checks below work on all four lanes with a free key; only the verification *submission* follows
> the chain tier. For the two gated chains the free web-UI "Verify & Publish" flow was used instead —
> no paid key was ultimately needed.

Commands run from the repo root (full ladder + expected pre-`activate` failures:
`RUNBOOK.md` § “Canary validation — all 4 lanes”):

```sh
just -E .env.<network> test-<network>-upgrade-state-verify  # production state-mate expectations;
        # expected to fail until the current on-chain setup completes handoff/finalization

just -E .env.<network> diffyscan            # explorer sources vs the commit pinned in
        # config/diffyscan/l2-<net>.yaml (Optimism/Base → Blockscout; Arbitrum/Linea → Etherscan v2)
```

Current results are expected to include production-state mismatches while the live deployments remain
pre-handoff/pre-finalization; diffyscan exact match for the OraclePool is 11/11 files.

## ACL setup

**Stage 1 (canary, current):** the deployer owns all three contracts and stands in for both CRE roles —
`owner()` = deployer on pool/trigger/receiver; `CREReceiver.getForwarder()` = deployer;
`CREReceiver.getExpectedAuthor()` = deployer. `CustomSender` (pre-existing proxy, per-lane address in
`<net>.inputs.yaml`) is untouched: `DEFAULT_ADMIN_ROLE` = Initial Owner, `SYNC_ROLE` still with the
legacy automation until `activate`.

**Final (post-`handoff` + `finalize`), asserted by the production state-mate profile
(`config/state/l2.yaml`):**

| Contract | Role / getter | Final holder |
|---|---|---|
| OraclePool, SyncTrigger, CREReceiver | `owner()` | LOL multisig (`l2LiquidityOwner` anchor, per lane) |
| CREReceiver | `getForwarder()` | Chainlink CRE Keystone forwarder (`l2CreForwarder` anchor) |
| CREReceiver | `getExpectedAuthor()` | LOL multisig |
| CustomSender | `DEFAULT_ADMIN_ROLE` (sole member) | Governance executor (`l2GovernanceExecutor` anchor) |
| CustomSender | `SYNC_ROLE` (sole member) | the new `SyncTrigger` |
| ProxyAdmin | `owner()` | Governance executor |

state-mate checks the **complete** role-member sets (via the `ozNonEnumerableAcl` sweep), not mere
membership — the legacy automation's `SYNC_ROLE` and the Initial Owner's admin are asserted **revoked**.

## What this deployment unlocks

Each unlock below is scoped **per lane** and rests on that lane's own evidence — a green lane does not
advance the others. Evidence on record for all four lanes includes the deploy broadcast
(`runDeployTest-latest.json`, commit-stamped in `<net>.deployed.yaml`) and exact-match source
verification binding the on-chain bytecode to the pinned repo commit. Production-only state-mate
checks remain red until migration completion.

**Unlocked next — the Stage-1 canary sync test** (`RUNBOOK.md` § “0→1 deploy + activate” / “Stage 1”),
per deployed lane, in order:

| # | Step | Actor | Remaining precondition |
|---|---|---|---|
| 1 | `fund-trigger` (0.5 ETH float) | Lido Deployer | deployer balance ≥ 0.5 ETH + gas — **currently held on Optimism only**; Arbitrum/Base/Linea hold ~0.05 ETH |
| 2 | `activate` (repoint pool, grant `SYNC_ROLE`) | Initial Owner | — (reversible; `rollback` stays available) |
| 3 | `verify-test`, then review production state-mate failures | Deployer (read-only) | canary checks pass; production delta is understood |
| 4 | `seed-test-weth` → wait 60 s → `simulate-sync` | Lido Deployer | a small WETH seed (≥ 0.0002 ETH) |

**Not unlocked by this deployment:**

* **`handoff` (1→2)** — gated on the lane's sync test succeeding (step 4 above), not on the deploy.
* **The L1 seal / `finalize` (3→4)** — a *cross-lane* gate: it requires **all four** lanes deployed,
  handed off and validated (RUNBOOK gate table, G3). All four are now deployed, but the gate also
  needs every lane's sync test and handoff — the deploys alone do not open it.
* **Production configuration** — the live contracts still run test knobs (0.0002 ETH / 60 s) and
  deployer ownership; nothing about the canary evidence certifies the production ACL table above.
  That claim is only established by the post-`handoff` production state-mate run.
